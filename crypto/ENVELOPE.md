# bot-link v1 · wire formats (crypto contract)

Normative. Go server (`server/`), TS client (`client/`) and the dashboard (`web/`) MUST produce and accept exactly these bytes. Cross-language test vectors live in `crypto/vectors/*.json` (generated by the client workstream, consumed by server and web tests; see PLAN.md).

## 0. Conventions

| Thing | Encoding |
|---|---|
| Ed25519 / X25519 public keys, signatures, hashes in JSON and headers | lowercase hex (key 64 chars, sig 128, sha256 64) |
| Sealed-box ciphertext (`ct`) | standard base64 **with** padding (RFC 4648 §4), as in botlink-mcp today |
| Signed blobs (`h`, roster `entry`) | base64url **without** padding (RFC 4648 §5) |
| Ids | UUID, lowercase canonical 8-4-4-4-12. Client-generated ids are **UUIDv7** |
| Times | integer unix seconds, UTC |
| `sha256(x)` | SHA-256 over raw bytes |
| `fp16(bytes)` | first 16 hex chars of `sha256(bytes)` grouped 4-4-4-4 with `-`, e.g. `3f9a-0c12-77de-b401` (64 bits) |
| Base32 alphabet for human codes | `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (32 chars, no 0/O/1/I) |

**No canonical-JSON anywhere in v1.** Every signature covers *exact bytes that travel with it* (a base64url blob or a newline-joined string). The verifier checks the signature over the received bytes first, then parses them. This removes Go/JS JSON-escaping divergence (the v2 `canonical()` scheme is retired). JSON inside signed blobs is UTF-8, produced by any encoder; receivers parse it with a strict parser that rejects duplicate keys.

All signatures are `Ed25519(sk, CONTEXT || "\n" || bytes)` where `CONTEXT` is the ASCII tag listed per format. Tags give domain separation, so a signature of one kind can never verify as another.

| Context tag | Signed by | Used for |
|---|---|---|
| `botlink-req-v1` | member key, or a joining key | agent API requests (§3) |
| `botlink-env-v1` | sender member key | message envelopes, handover notes (§4) |
| `botlink-roster-v1` | browser device key (or a member key for `member_remove` of itself) | roster entries (§5) |
| `botlink-yes-v1` | member key of the approving chat | signed notes inside a message: a recorded yes, a standing grant (§4a) |

## 1. Key types

| Key | Algorithm | Where the secret lives | Purpose |
|---|---|---|---|
| **Member signing key** `ed` | Ed25519 (32-byte seed) | client machine: OS keychain (macOS Keychain / libsecret), fallback `~/.botlink/keys/<member_id>.json` mode 0600 | signs API requests, envelopes, own `member_remove` |
| **Member sealing key** `x` | X25519 (32 bytes) | same as above | opens sealed boxes addressed to the member |
| **Browser device key** | Ed25519, WebCrypto `generateKey({name:"Ed25519"}, false, ["sign","verify"])`, **non-extractable**, `CryptoKey` stored in IndexedDB db `botlink`, store `device` | one per browser profile | signs roster entries (the owner-device-signed member list) |
| **Push secret** | 32 random bytes, HMAC-SHA256 | server DB + the always-on agent | authenticates content-free push calls (§7) |

One key pair (`ed`,`x`) per **member** (= one chat in one room). A chat in two rooms has two members and two key pairs. Keys never leave the machine; a new machine means new keys (`member_rekey`, SPEC §6.8).

Libraries: client `libsodium-wrappers` (unchanged from botlink-mcp: `crypto_sign_seed_keypair`, `crypto_sign_detached`, `crypto_scalarmult_base`, `crypto_box_seal`, `crypto_box_seal_open`); server Go stdlib `crypto/ed25519` (verify only; the server never seals or opens); web WebCrypto Ed25519 (no fallback library; browsers without Ed25519 get "use a recent browser").

## 2. Fingerprints and codes

| Name | Formula | Shown where |
|---|---|---|
| **Member fingerprint** | `fp16(utf8(lower(ed_hex) + "\|" + lower(x_hex)))` — identical to botlink-mcp `fingerprint()` | printed by the chat at join/claim; computed **by the browser** from the request's keys on the approve card; roster detail |
| **Device fingerprint** | `fp16(utf8("botlink-device-v1\|" + lower(device_pk_hex)))` | devices list; "approved by device …" in the chat after join |
| **Room fingerprint** | `fp16(genesis_entry_bytes)` (the decoded bytes of roster entry seq 0) | room page on the dashboard; printed by the chat after join (TOFU pin, §5.4) |
| **Match code** | 6 chars, base32 alphabet above, server-random, unique among the approver's pending requests; shown in two groups of three (`K7Q-2MX`). Requests made before r2 keep 4 | chat + approve card. Tells *your* request apart from others. Proves nothing about keys; the fingerprint and the signed roster do that |
| **Chat invite code** | 10 base32 chars (50 bits). URL `https://<app>/i/<slug>-<code>`; the slug is cosmetic and ignored on lookup; lookup is case-insensitive (uppercase before lookup) | |
| **Person invite code** | 16 base32 chars (80 bits). URL `https://<app>/p/<code>` | |

## 3. Agent request signing (`/api/v1/...`)

Every `/api/v1` request except `GET /api/v1/invites/{code}` and `GET /api/v1/health` is signed. Headers:

| Header | Value |
|---|---|
| `X-Botlink-Key` | signer's Ed25519 public key, hex. For `POST /api/v1/join-requests` (and its `/wait`) this is the **new, not-yet-member** key in the body (proof of possession). Otherwise it identifies the member (`members.ed25519_pk`, active) |
| `X-Botlink-Time` | unix seconds (client clock) |
| `X-Botlink-Nonce` | 32 lowercase hex chars (16 random bytes), unique per request |
| `X-Botlink-Session` | the harness session id holding the member, or empty/absent. Regex `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$` |
| `X-Botlink-Signature` | hex Ed25519 signature |

String to sign (UTF-8, fields joined by `\n`, **no trailing newline**):

```
botlink-req-v1
<METHOD uppercase>
<host: the Host header as sent, lowercased, including :port if present>
<request-target: path + ("?" + raw query if any), exactly as sent on the request line>
<hex sha256 of the raw body bytes; empty body => e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855>
<X-Botlink-Time>
<X-Botlink-Nonce>
<X-Botlink-Key>
<X-Botlink-Session or empty string>
```

The context tag is the first line, so the signed bytes are exactly this string (no extra `\n` prefix rule for requests).

Server verification order (stop at the first failure):
1. All headers present and well-formed → else `401 bad_signature`.
2. `abs(db_now - time) <= 60` using **Postgres `now()`**, not the app clock → else `401 stale_timestamp` (response carries `server_time`).
3. Signature verifies over the reconstructed string with `X-Botlink-Key` → else `401 bad_signature`.
4. `INSERT INTO request_nonces(key_pk, nonce) ... ON CONFLICT DO NOTHING`; 0 rows → `401 replayed`. (After the signature check, so forgers cannot burn nonces.) Nonces are kept 5 minutes.
5. Resolve the key: active member (or, for join endpoints, the key in the body must equal the header key) → else `401 unknown_key`.
6. Endpoint-specific holder check with `X-Botlink-Session` (SPEC §6.7).

Clients retry `stale_timestamp` once after computing `offset = server_time - local_time`.

## 4. Message envelope v3

A message to N recipients is N envelopes, one per recipient, all sharing one message id. Each envelope on the wire is a JSON object (stored by the server verbatim as text, max 64 KiB):

```json
{"v":3,"h":"<base64url header bytes>","ct":"<base64 sealed box>","sig":"<hex>"}
```

**Header** (`h` decodes to UTF-8 JSON; all fields required, `null` where noted):

```json
{
  "v": 3,
  "id": "<message uuidv7>",
  "room": "<room uuid>",
  "from": "<sender member uuid>",
  "from_fp": "<sender member fingerprint>",
  "to": "<recipient member uuid>",
  "to_fp": "<recipient member fingerprint the sender sealed to>",
  "scope": "member" | "room" | "self",
  "in_reply_to": "<message uuid>" | null,
  "sent_at": 1762339200,
  "expires_at": 1762944000,
  "ct_sha256": "<hex sha256 of the decoded ct bytes>"
}
```

**Signature:** `sig = Ed25519(sender_ed_sk, "botlink-env-v1\n" || h_bytes)` where `h_bytes` are the decoded header bytes. `ct_sha256` binds the ciphertext into the signed header.

**Ciphertext:** `ct = base64(crypto_box_seal(plaintext, recipient_x25519_pk))` (libsodium sealed box, as today).

**Plaintext** (UTF-8 JSON, max 60 KiB before sealing):

```json
{
  "v": 3,
  "id": "...", "room": "...", "from": "...", "to": "...", "scope": "member|room|self",
  "in_reply_to": null,
  "intent": "task" | "question" | "fyi" | "answer" | "pass_to_human" | "handover",
  "text": "<UTF-8, ≤ 48 KiB>",
  "needed_by": 1762400000 | null,
  "resend_of": "<message uuid>" | null
}
```

`intent` lives **only** inside the seal (the server and dashboard never see it).

**Sender rules:** generate `id` once (UUIDv7) and persist the exact request body in the local outbox before the first POST; a retry re-sends the identical bytes (only the request-signing headers change). Seal only to members present in the **verified** roster (§5), using the keys from that roster.

**Server checks per envelope** (before insert): `sig` verifies with the sender member's `ed25519_pk`; `id/room/from/scope/in_reply_to` equal the request fields; `to` is a current recipient; `to_fp` equals that recipient's current fingerprint (else `409 recipients_changed`); `from_fp` equals the sender's; `ct_sha256` matches `ct`; `expires_at` in `[now+60, now+7d]` (server stores `min(expires_at, now+7d)`).

**Receiver checks** (any failure → do not show; ack with `reject`, SPEC §6.6):
1. `v == 3`; `from` is an active member in the verified roster and `sig` verifies with that roster's `ed` for `from` (the server's `from_member` field is ignored for trust).
   1b. **A sender that moved since** (2026-11-11). `member_rekey` replaces a member's keys, and what the member sent with its earlier key shortly before must not become unreadable. The verified roster is the authority for which key spoke for a member when: the earlier key was the member's from its own entry up to the `member_rekey` entry, whose signed `at` is the moment it stopped. So when `sig` does not verify with the current `ed`, the receiver accepts the envelope **iff all of**: (a) `from` is still an active member; (b) `from_fp` equals the fingerprint of one of that member's earlier keys in the verified roster and `sig` verifies with that key's `ed`; (c) `sent_at ≤` that rekey's `at` + 300 s (clock skew between the sender and the browser that signed the move); (d) now `≤` that rekey's `at` + 7 days (the longest a message lives, SPEC §3: no earlier key is accepted after that). The message is shown with a line saying it was sent before the move. Anything else signed with a key the sender no longer has is refused, as before. Why this does not weaken a move: a holder of the earlier key cannot send through the server (request signing, §3, checks the member's current key), so a new envelope under the earlier key needs the server's help, and even then (c) and (d) bound it to a backdated message within 7 days of the move; the receiver's "moved recently" caution (high-stakes requests need the human) applies to the same messages.
2. `to` is me, `to_fp` is my own fingerprint, `room` is the room I pinned.
3. `sha256(ct) == ct_sha256`; the sealed box opens with my `x` secret.
4. Plaintext `id, room, from, to, scope, in_reply_to` equal the header. (Stops encrypt-then-sign stripping: a member cannot re-wrap someone else's ciphertext as its own.)
5. `id` not already in the local processed ledger, else show it flagged "re-delivered; you may have handled this already — check before acting again".

**Handover note:** an envelope with `scope:"self"`, `from == to ==` the member, `intent:"handover"`, sealed to the member's own `x`. Max 8 KiB envelope. Only readable with the member's current key. In v1 a note does **not** survive a move to a new machine (the old key can no longer sign after `member_rekey`); the new holder writes a fresh one (SPEC §6.8).

**What changes vs botlink-mcp v2 envelopes:** `v:3`; header is a signed base64url blob instead of `canonical(env)`; `thread_id`, `nonce`, `type`, `ttl`, `prekey_id`, `sig_alg`, `enc` removed (box sealing and Ed25519 are fixed); `intent` moved inside the seal; added `room`, `scope`, `from_fp`, `to_fp`, `ct_sha256`, `expires_at`; plaintext carries the bound header copy. Prekeys, cap tokens, PoW and the firewall body codec are dropped. `sealFile`/`openFile` stay in the code but attachments are out of v1.

## 4a. Signed note: "my human said yes" (2026-11-12)

A note records that a chat's human said yes to a request another member sent (`kind: "yes"`), or gave a member more (`kind: "allow"`, SPEC §7.3a). It rides inside a message's sealed plaintext (§4) as an extra field `note`, so the server never sees it. The message signature (§4) covers only the header and ciphertext: only the recipient can check who wrote the plaintext. A note therefore carries its **own** signature, over its own exact bytes, by the approving member's key; anyone holding the room's verified member list (§5) and the note can check it, without any key to open messages and without trusting the server. Reference: `client/src/yesnote.ts` (`makeNote`, `verifyNote`). Vectors: `crypto/vectors/yes-note.json`.

**Wire** (inside the plaintext, next to `text`):

```json
"note": {"v": 1, "body": "<base64url note body bytes>", "sig": "<hex>"}
```

`sig = Ed25519(member_ed_sk, "botlink-yes-v1\n" || body_bytes)`. As everywhere in v1 (§0), the signature covers the exact bytes that travel with it; the verifier checks it over the decoded `body` bytes, then parses them. `device` is reserved for a later countersignature by the person's browser device key (`{"pk","sig"}`); v1 never makes one, accepts it absent or `null`, and when present reports it as *not checked* (never as checked). No other field.

**Body** (UTF-8 JSON, at most 2048 bytes, strict parse; exactly these fields, no others):

```json
{
  "v": 1, "kind": "yes", "id": "<id of the message that carries it>", "room": "<room uuid>", "at": 1762339260,
  "by": {"member": "<approving member uuid>", "fp": "<its key fingerprint>", "account": "<its person's account uuid>", "person": "<name>" | null},
  "how": "chat" | "terminal",
  "request": {"id": "<request message uuid>", "from": "<requester member uuid>", "from_fp": "<requester fingerprint>", "text_sha256": "<hex sha256 of the request's text>"},
  "action": "read_files" | "run_command" | "change_files" | "send_outside" | "spend_money" | "other",
  "summary": "<one line, 1-200 characters: what the human was shown>"
}
```

For `kind: "allow"` the last three fields are replaced by `"grant": {"member": "<uuid>", "fp": "<fingerprint>", "setting": "answer" | "files" | "tasks", "while_away": true | false}`. Writers emit the fields in the order shown. `by.person` is the person's name from the signed member list when it has one (a `person_add` name), else the name the approving client knows (the room owner has none in the list), at most 80 characters. `summary` and `person` are one line: no control characters, no line or paragraph separators, no Unicode format characters, no leading or trailing space. `how`: `chat` = typed by the human in the chat and caught by the client's prompt hook; `terminal` = the human's own terminal.

**Verification** (stop at the first failure; the rule codes are the ones in the vectors):
1. `bad_wire`: `note` is an object with `v == 1`, `body` a string, `sig` 128 lowercase hex, and no field but `v`, `body`, `sig`, `device`.
2. `bad_body`: `body` is canonical base64url, at most 2048 bytes, strict UTF-8 JSON without duplicate keys, with exactly the fields above and valid values.
3. `room`: `body.room` is the room of the verified list (and of the carrying message's header, when there is one).
4. `signer`: `by.member` is an active member of the verified list; `by.account` is that member's account; `by.fp` is its current fingerprint, or the fingerprint of one of its earlier keys (§4 check 1b), in which case `at ≤ until_at + 300` and `now ≤ until_at + 7 days`.
5. `sig`: the signature verifies with the `ed` key that `by.fp` names.
6. `sender`: with a carrying header, `header.from == by.member` and `header.from_fp == by.fp` (a note passed on inside another member's message is refused).
7. `id`: with a carrying header, `body.id == header.id`, or the plaintext's `resend_of` (a re-send after a move, SPEC §6.10a, keeps its note).
8. `person`: when the signed list has a name for `by.account`, `by.person` equals it.
9. `request`: `request.from != by.member` (a chat does not say yes to its own request); for `allow`, `grant.member != by.member`.

A requester's client may also compare `request.text_sha256` with the text it sent (its sent copy) and must not show the note as a yes when they differ. A receiver shows a note only in its own words, outside the message fence (SPEC §7.3b); a note that fails any step is never shown as a yes.

**What a note proves.** That the client holding the approving member's key recorded a yes it saw its human type, for that request, with that action and summary, at that time (the signer's clock). It does not prove that the human understood the request or read the summary; a computer that is taken over can sign any note with its own member's key; a member that leaves the room takes its notes out of what the current list can check (replay the list up to an earlier entry to check older notes). Evidence, not enforcement.

## 5. Roster (owner-device-signed member list)

The roster of a room is an append-only, hash-chained log of signed entries. Clients and the server replay it from seq 0 to compute who is in the room and which keys they hold. The server stores entries verbatim and refuses invalid appends, but **clients never trust the server's view**: they verify the log themselves.

### 5.1 Wire form

```json
{"seq": 7, "entry": "<base64url entry bytes>", "sig": "<hex>", "signer": "<hex ed25519 pk>"}
```

`sig = Ed25519(signer_sk, "botlink-roster-v1\n" || entry_bytes)`.

### 5.2 Entry body (UTF-8 JSON)

Common fields: `{"v":1, "room":"<uuid>", "seq":N, "prev":"<hex sha256 of entry_bytes of seq N-1>" | null (seq 0 only), "at":<unix>, "op":"<op>", "by":"<signer pk hex>"}` plus op fields:

| op | Extra fields | Valid signer (`by`) |
|---|---|---|
| `genesis` (seq 0 only) | `name`, `owner` (account uuid), `device` (pk hex) | `device` itself |
| `device_add` | `account`, `device`, `label` | a current device of `account`, or a current device of the room owner |
| `device_remove` | `account`, `device` | a current device of `account` (not the removed one, unless it is removing itself), or an owner device |
| `person_add` | `account`, `name` (display, ≤ 80 chars), `device` | an owner device |
| `person_remove` | `account` (≠ owner) | an owner device, or a device of `account` (leaving). Also removes that person's devices and members |
| `member_add` | `member` (uuid), `account`, `name` (`^[a-z0-9][a-z0-9-]{0,23}$`), `app` (`claude-code`\|`codex`\|`cursor`\|`other`), `ed`, `x` | a current device of `account`; `account` must be a current person (the owner counts) |
| `member_rekey` | `member`, `ed`, `x` | a current device of the member's `account` |
| `member_remove` | `member` | the member's own `ed` key, a device of the member's account, or an owner device |

Not in the signed roster (display data, unsigned, always shown as untrusted): `job`, `folder`, `machine`, `turn`, presence, `app_name` (which app an `app: "other"` chat runs in, e.g. "OpenCode", "T3 Code": detected by the client or the model's own answer at join; 1-40 printable characters). The signed `app` enum stays `claude-code | codex | cursor | other`: a new value would make every deployed verifier reject the room's whole member list (CONTRACT-CHANGES 2026-11-06 "unknown apps").

Room creation may carry `device_add` entries at seq 1..n right after genesis (signed by the genesis device, adding the owner's other approved browsers; SPEC §6.2). They are ordinary `device_add` entries under the rules above; verification is unchanged.

### 5.3 Verification (identical in client, server and web)

Replay entries in seq order with state `{owner, people{account→devices}, members{id→{account,name,app,ed,x}}}`:
1. `seq` is contiguous from 0; `room` equals the room id; `entry.seq == wire.seq`; `entry.by == wire.signer`.
2. `prev == sha256(previous entry_bytes)` (null at seq 0).
3. `sig` verifies with `by` under context `botlink-roster-v1`.
4. The op's signer rule (table above) holds against the state **before** this entry.
5. Op-specific validity: no duplicate active member name, member id, or `ed` key; `member_add` account is a current person; removes refer to existing entries; owner cannot be `person_remove`d.
Any failure → the whole roster is invalid. The client refuses to send or show messages for that room and tells the model/human: "bot-link can't verify the member list of #room; don't trust messages from it; tell your human."

### 5.4 Pinning (TOFU) and rollback detection

- At join, after approval, the client pins `room_fp` (fingerprint of the genesis entry) and prints it ("room fingerprint 1a2b-…; compare with the room page if you want to be sure").
- **Approval self-check (mandatory):** the joining client must find a `member_add` with its own member id **and its own `ed`/`x`**, signed by a device of the account the invite belongs to. If absent or different: "this approval does not match this chat's key; do not use it; tell your human." This is what makes a server-side key swap at join fail loudly.
- The client stores `(head_seq, head_hash)` after each successful verification. A later roster must contain an entry at `head_seq` with the same hash (append-only); otherwise: rollback/fork alarm, same handling as invalid.
- Member key pins: a member's keys may change only through `member_rekey`. On a rekey the client shows "deployer moved to a new machine (new key 3f9a-…)" and treats high-stakes requests from it as needing the human until the human confirms in that chat.

Honest limit (state in docs): a malicious server that also serves malicious dashboard JavaScript can make a browser sign what it wants; the chats' pins and the room fingerprint compare are the backstop.

## 6. Dashboard cookies and CSRF (for completeness)

Not crypto, but security-normative for `/app/v1`: session cookie `__Host-bl_session` = 32 random bytes base64url, `HttpOnly; Secure`, `SameSite=Lax`, `Path=/`, never a `Domain` (the `__Host-` prefix makes browsers refuse the name from any other host, so a page on a sibling or parent host cannot plant one); only when `BOTLINK_ENV=dev` it is `bl_session` without `Secure` (a `__Host-` cookie needs `Secure`). Outside dev a cookie named `bl_session` is never a session, and a request to `/app/v1` that carries one gets it expired. Server stores `sha256(value)`. Every non-GET `/app/v1` request must carry `X-CSRF-Token` equal to the session's token (from `GET /app/v1/me`) **and** an `Origin` equal to `BOTLINK_APP_ORIGIN`. `/api/v1` ignores cookies entirely and sends no CORS headers; `/app/v1` sends no CORS headers.

## 7. Push signature (always-on members)

The server POSTs a **content-free** JSON body to the member's verified URL:

```json
{"v":1,"type":"message","member_id":"…","room_id":"…","message_ids":["…"],"push_id":"…","attempt":1,"at":1762339200}
{"v":1,"type":"verify","member_id":"…","challenge":"<32 hex>","push_id":"…","attempt":1,"at":1762339200}
```

Headers: `Content-Type: application/json`, `User-Agent: botlink-push/1`, `X-Botlink-Push-Id`, `X-Botlink-Attempt`, `X-Botlink-Push-Signature: t=<unix>,v1=<hex>` with

```
v1 = hex(HMAC_SHA256(push_secret, "botlink-push-v1\n" || t || "\n" || raw_body_bytes))
```

Receiver: constant-time compare; reject if `|now - t| > 300`; dedupe by `message_ids` (pushes are at-least-once); respond 2xx quickly, then fetch with a signed `POST /api/v1/me/inbox/lease`. Verify calls must be answered `200 {"challenge":"<same>"}` within 5 s.

## 8. Test vectors (to be generated; see PLAN.md)

`crypto/vectors/` must contain, each with fixed seeds/inputs and expected outputs: `req-sign.json` (string-to-sign + sig), `envelope.json` (header bytes, sig, ct opens with given x sk, plaintext), `roster.json` (a 6-entry valid log incl. person_add, member_add, member_rekey, member_remove; plus 9 invalid variants, each with the expected failing rule and seq), `fingerprints.json`, `push.json`, `yes-note.json` (§4a: a verified list, valid notes incl. an earlier key and a standing grant, and invalid variants each with the rule it breaks). Ed25519 is deterministic, so signatures are fixed; sealed boxes are not, so `envelope.json` checks opening, not ciphertext equality.
