# crypto/vectors

Cross-language test vectors for `crypto/ENVELOPE.md` §8. Generated by the client workstream from fixed seeds
(`seed(name) = sha256("botlink-vector-v1|" + name)`) with `cd client && npm run vectors`, and cross-checked by an
independent implementation (PyNaCl + hashlib, its own replay of the member-list and yes-note rules, written from the
spec): `python3 client/scripts/check-vectors.py crypto/vectors`. It runs every file, including each invalid member list
(rule and seq) and each yes-note case (valid, and invalid with its rule).

Encodings follow ENVELOPE §0: keys/sigs/hashes lowercase hex; `entry` and envelope `h` base64url without padding;
sealed-box `ct` standard base64 with padding. Ed25519 seeds are the 32-byte libsodium/RFC 8032 seed.

| File | What to check |
|---|---|
| `fingerprints.json` | `fp16`, member fingerprint (`utf8(lower(ed) + "\|" + lower(x))`), device fingerprint (`"botlink-device-v1\|" + pk`), the base32 alphabet. The third member case gives uppercase hex: lowercase before hashing. |
| `req-sign.json` | For each case, rebuild `string_to_sign` from `method` (uppercased), `host` (lowercased), `target` (verbatim, incl. query), `sha256(body utf-8)`, `time`, `nonce`, `key`, `session` (empty string if none) joined by `\n`, no trailing newline; `sig = Ed25519(seed, utf8(string_to_sign))`. Signatures are deterministic: compare exactly. |
| `roster.json` | `valid.entries` (6 entries: genesis, person_add, member_add by the owner's device, member_add by the friend's device, member_rekey, member_remove signed by the member's own key) must verify and yield `valid.expect` (room fp, head, people, active members). `valid.entry_json` are the decoded entry bytes for reading. Each `invalid[i]` must be rejected with `expect.rule` at `expect.seq`. |
| `envelope.json` | `envelope.sig` verifies over `"botlink-env-v1\n" + header bytes` with `sender.ed`; `sha256(base64decode(ct)) == header.ct_sha256`; `ct` opens (sealed box) with `recipient.x_sk` to exactly `plaintext_json`. `ct` is random per generation, so check opening, never equality. `invalid` variants must fail the signature check. |
| `yes-note.json` | ENVELOPE §4a. Verify `roster` for `room_id` (§5), then each case against that list with `now`: every `valid[i]` checks out (`expect.kind`, `expect.earlier_key`, `expect.device`; `body_json` is the decoded body); every `invalid[i]` fails with `expect.rule`. `header` is the carrying message's header fields (`null`: the note alone); `resend_of` is the carrying plaintext's. Rules in order: `bad_wire`, `bad_body`, `room`, `signer`, `sig`, `sender`, `id`, `person`, `request`. Generated by `node --import tsx client/test/gen-yes-vectors.ts` (from `client/`: `node --import tsx test/gen-yes-vectors.ts`). Signatures are deterministic: the client test compares the committed file with a fresh build. |
| `push.json` | `v1 = hex(HMAC_SHA256(hex_decode(secret), "botlink-push-v1\n" + t + "\n" + body))`, header `t=<t>,v1=<v1>`. |

## Roster rule codes (shared; the server uses them in `roster_invalid` `details.rule`)

Verification runs in this order per entry and stops at the first failure (ENVELOPE §5.3):

| Code | Meaning (step) |
|---|---|
| `bad_wire` | wire object malformed: `seq` not an integer, `entry`/`sig` not strings, `signer` not 64 lowercase hex |
| `seq` | §5.3.1 wire `seq` is not the next contiguous number from 0 (checked before decoding), or `entry.seq != wire.seq` |
| `bad_entry` | entry bytes are not base64url, > 4096 bytes, not strict UTF-8 JSON (duplicate keys, comments and trailing commas rejected), or a common field is missing/mistyped (`v` must be 1, `seq`/`at` integers, `room`/`op`/`by` strings) |
| `room` | §5.3.1 `entry.room` is not this room |
| `by` | §5.3.1 `entry.by != wire.signer` |
| `prev` | §5.3.2 `prev` is not `sha256(previous entry bytes)` (or not `null` at seq 0) |
| `sig` | §5.3.3 Ed25519 signature under `botlink-roster-v1` does not verify with `by` |
| `signer` | §5.3.4 the signer is not allowed for this op (table in ENVELOPE §5.2), checked against the state before the entry |
| `op` | §5.3.5 op validity: unknown op, malformed op fields, genesis not at seq 0 / non-genesis at seq 0, duplicate active member name / member id / `ed`, `member_add` for an account that is not a current person, references to unknown members/devices/people, `person_add` of an existing person or device, removing the owner |

Exact order inside one entry: `bad_wire` → `seq` (wire) → `bad_entry` → `seq` (entry vs wire) → `room` → `by` → `prev` → `sig` → `signer`/`op` (the op handler checks field shape (`op`) before the signer rule (`signer`), then the remaining op rules; for `member_rekey` / `member_remove` an unknown member is an `op` failure before the signer rule, because the rule needs the member's account). Reference implementation: `client/src/roster.ts` `verifyRoster`.
